# Using S3 or MinIO for attachments

Set `blob_backend=s3` and the `s3_*` settings (see [CONFIGURATION.md](CONFIGURATION.md)). `blob_dir` then holds only
upload staging on local disk; committed files live in the bucket under `ab/cd/<sha256>`, so identical files are stored once.

```
TASKLANE_BLOB_BACKEND=s3
TASKLANE_S3_BUCKET=tasklane-files
TASKLANE_S3_REGION=eu-west-1
TASKLANE_S3_ACCESS_KEY_FILE=/run/secrets/s3_access_key
TASKLANE_S3_SECRET_KEY_FILE=/run/secrets/s3_secret_key
# MinIO or another compatible service:
TASKLANE_S3_ENDPOINT=http://minio:9000
```

`tasklane doctor` writes and deletes a test object, so a wrong key, region, endpoint, bucket or permission is reported
there rather than on the first upload. `/readyz` includes the same check (cached for 15 seconds).

The IAM policy needs `s3:PutObject`, `s3:GetObject`, `s3:DeleteObject`, `s3:ListBucket`, `s3:AbortMultipartUpload` and
`s3:ListBucketMultipartUploads` on the bucket. Turn on a lifecycle rule that aborts incomplete multipart uploads after a few
days as a safety net; the application cleans up its own.

## Direct uploads from the browser

Files over 8 MiB go from the browser straight to the bucket in parts with presigned URLs; the server only hands out the URLs
and, at completion, reads the object back to check its size, hash, type, malware signature and archive limits before it
becomes visible under its hash. Nothing is visible, and no attachment exists, before that. For this the bucket needs a CORS
rule for the Tasklane origin:

```json
[{"AllowedOrigins": ["https://tasklane.example.com"], "AllowedMethods": ["PUT"], "AllowedHeaders": ["*"], "ExposeHeaders": ["ETag"], "MaxAgeSeconds": 3000}]
```

The page's Content-Security-Policy allows the bucket origin automatically (and only it). Without the CORS rule the browser
reports the upload as interrupted and the person can retry; nothing is left behind.

## Behaviour to know about

- Writes retry with exponential backoff on throttling (`503 SlowDown`) and server errors, five attempts; `403` is not retried.
- An upload larger than the part size (16 MiB by default) uses a multipart upload that is aborted on failure.
- Server-side encryption is requested with `s3_sse` (`AES256` or `aws:kms` with an optional `s3_kms_key_id`).
- `tasklane` verifies the SHA-256 of every object it commits (single requests carry the checksum for the service to verify).
- Integrity checks (`fsck`), the garbage collector and bundle export work the same on both backends.

## Moving between backends (`fs` and `s3`) without downtime

The same procedure works in both directions (a rollback is the same move the other way).

1. Set `blob_backend` to the **new** backend and `blob_fallback` to the **old** one (`blob_fallback_dir` is the old directory when the old one is `fs`; with `s3` as the old one it uses the `s3_*` settings). Restart. From now on new uploads go to the new backend only; a read that the new backend cannot answer is served from the old one and copied across, so attachments keep working and the busiest ones move first.
2. Run `tasklane blobs migrate --verify` while the server is up. It copies every object the database knows about that the new backend lacks, streaming each one and checking its SHA-256 on the way (an object whose bytes do not hash to its name is reported and never copied), and with `--verify` reads each copy back. It is safe to stop and to run again: what is already there is skipped. Nothing is ever removed from the old backend.
3. Run `tasklane blobs verify`: it checks, against the new backend alone, that nothing the database refers to is missing or damaged.
4. Set `blob_fallback=none` and restart. Keep the old backend until you are sure; to go back, swap the two settings and repeat from step 2.

An empty file is a normal attachment; earlier versions could not store one on S3 (the request was refused as chunked), which this move would have hit.
